2. VULNERABILITY MECHANISM & FAIL-CLOSED HAZARD
--------------------------------------------------------------------------------
- Trigger Conditions:
  1. Non-canonical status string supplied with success=True (e.g. {'status': 'partial', 'success': True}, {'status': 'pending', 'success': True}, {'status': 'draft', 'success': True}).
  2. Null or empty status key supplied with success=True (e.g. {'status': None, 'success': True}, {'status': '', 'success': True}).
  3. Contradictory dict claiming success=True alongside non-success status candidates (e.g. {'status': 'warning', 'success': True}, {'status': 'blocked', 'success': True}, {'status': 'failed', 'success': True}, {'status': 'inconclusive', 'success': True}).
- Flaw in Previous Behavior:
  1. When raw_status was None (e.g. {'status': None, 'success': True}), status parsing was bypassed, leaving status_candidate=None. Because "success" was in result, the normalizer fell into the else branch: canonical_status = "success", success = True, falsely manufacturing clean success out of an invalid null status.
  2. Contradiction checks lacked an explicit verification rule detecting result.get("success") is True paired with non-success status candidates ('failed', 'blocked', 'inconclusive', 'warning'). Such dictionaries escaped explicit contract violation tagging (error_code remained GENERIC_ERROR instead of INVALID_RESULT_CONTRACT).
  3. Arbitrary non-canonical status strings could enter ambiguous states without clear diagnostic contract violation enforcement.
